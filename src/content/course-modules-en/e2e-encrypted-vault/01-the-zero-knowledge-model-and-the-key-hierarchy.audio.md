Chapter one. The zero-knowledge model and the key hierarchy. Storing your files on someone else's machine without them being able to read anything: an irreversible architecture choice, a hierarchy of envelopes, and a subtle attack on key derivation.

You want to store your files on a server: yours, a hosting provider's, it does not matter. The question that shapes the whole architecture fits in one sentence: who holds the keys? The answer commits everything else, down to how an image thumbnail gets generated or how a sharing link works.

There are two trust models. Model one: server-side encryption. The server encrypts your data at rest and in transit, but it holds the keys. The benefits are immediate: the server can generate previews, index content for search, recover a forgotten password. The cost is just as immediate: the server, and whoever compromises it, administers it, or legally compels it, can read your files. Model two: end-to-end encryption, also called zero-knowledge. The keys never leave your devices. The server only sees opaque blobs: it stores, it serves, it understands nothing. The cost: every feature that required reading the content moves client-side, and a lost password cannot be reset by support, because there is mathematically nothing to reset.

Keep this in mind: zero-knowledge is not a feature you add in version two. It is a decision that constrains the storage format, the protocol, and the design of every screen. Retrofitting end-to-end onto a system designed server-side means re-encrypting all the data and rewriting every feature that read content. Going the other way is trivial. Which is exactly why you choose before the first stored byte.

The single-password problem. Everything starts from a human secret: a passphrase. And immediately, two contradictory requirements appear. On one hand, the server must be able to authenticate the user: it needs something derived from the passphrase. On the other hand, the passphrase must produce the encryption key for the data, and that one, the server must never see. The standard solution: a domain-separated double derivation. The passphrase goes once through an expensive derivation function, Argon2id, producing a pre-key. That pre-key is then stretched into two independent keys by a fast derivation with two distinct contexts: an auth key, sent to the server, which re-hashes it before storing it; and a master key, which never leaves the client. Knowing one tells you nothing about the other. The server authenticates without being able to decrypt.

Why Argon2id? A human passphrase has little entropy: each brute-force attempt must be made expensive. Argon2id is a memory-hard function: every evaluation requires tens of megabytes of memory, which neutralizes massively parallel GPU attacks.

The envelope hierarchy. Could we encrypt all files directly with the master key? Yes, and it would be a mistake. The day you change your passphrase, the master key changes, and you would need to re-encrypt terabytes. The remedy is envelope encryption: each key encrypts only one other key, and only the last one encrypts data. The account key is random, it derives from nothing; it is stored on the server, encrypted under the master key. Changing your passphrase means re-encrypting that single envelope: thirty-two bytes, not terabytes. The file keys are random too, one per file, each stored encrypted under the account key. And the recovery key is a second envelope of the account key: generated at registration, displayed exactly once as a printable code, it is the only safety net if the passphrase is lost. In a zero-knowledge system, losing the passphrase without a recovery kit means losing the data, and it is provable: the server holds nothing that could recover it.

The parameter-downgrade attack. Here is the subtlety that separates a correct design from a design that looks correct. The Argon2id parameters are stored server-side: the client needs them to re-derive the same keys at every login. So, at login time, the server announces the parameters to the client. Do you see the attack? A compromised server replies: your parameters are eight megabytes of memory, one iteration. The client obeys, derives with those weak parameters, sends the corresponding auth key. The server now holds a hash derived through a function that is trivial to attack: offline brute force on the passphrase becomes practical again, and with it the reconstruction of the master key. The defense is simple and must live client-side: a validation floor. The client refuses any derivation whose parameters fall below a hard-coded minimum. Weak parameters do not produce a weak derivation: they produce an error.

This is a general reasoning pattern: in a protocol where an untrusted party supplies security parameters, the other party must enforce a floor.

Key takeaways. Two trust models, and an irreversible choice made before the first stored byte. The double derivation splits what the server must know from what it must never see. The envelope hierarchy localizes every change: new passphrase, thirty-two re-encrypted bytes. The recovery kit is indispensable, because without it, losing the passphrase is unrecoverable. And when an untrusted party supplies security parameters, you enforce a floor: without a client-side KDF floor, a compromised server can make the passphrase brute-forceable remotely.
