Chapter three. Chunking, content addressing and Merkle trees. Splitting files where their content decides, addressing each chunk by its digest, and organizing everything into an encrypted tree the server hosts without ever seeing it.

We know how to encrypt a blob and bind it to its role. What remains is deciding what to encrypt: a twenty-gigabyte file is not one blob. To resume an interrupted transfer, to re-upload only what changed, to avoid saturating memory, you must split. And once files are split into anonymous chunks, something must remember the directory tree, without the server, which stores that something, being able to read it.

Split where the content decides. The naive approach cuts fixed-size blocks. It has a fatal flaw for synchronization: insert one byte at the start of a file, and every boundary shifts. Every block changes, everything must be re-uploaded. Content-defined chunking, the FastCDC algorithm, places boundaries where a rolling fingerprint of the local content hits a particular pattern. Boundaries are attached to the content, not to positions: insert a byte at the start, and only the boundaries in the immediate neighborhood move. Modifying one kilobyte in the middle of a two-gigabyte file only invalidates the chunk or chunks it touches. This is the foundation of differential synchronization. Sizes are bounded, for instance one, four and sixteen megabytes, and the pipeline works streaming: one chunk in memory at a time, never the whole file.

Content addressing. Each chunk, once encrypted, gets its address: the digest of its ciphertext. That address is what the server knows: to it, the vault is just a collection of digest-addressed blobs. Three properties follow. One: integrity is verifiable without a key. On download, the client recomputes the digest of the received blob; if it differs from the requested address, the blob was altered or substituted, detected before even attempting decryption. Two: uploads are idempotent, retry-on-error becomes trivial. Three: the server can verify writes without understanding anything about the content.

Why the digest of the ciphertext and not the plaintext? Because the address is visible to the server: a plaintext digest would hand it a membership test. Does this user own this known file? The ciphertext digest, which depends on a random file key, reveals nothing.

And this is where the refusal of cross-user deduplication plays out. If two users upload the same movie, could we store it once? That would require identical content to produce identical ciphertext: convergent encryption, where the key derives from the content. But that scheme is vulnerable to confirmation attacks: anyone holding a candidate file can encrypt it the same way and check, via the address, whether someone else has it. For a vault, that is disqualifying. Our file keys are random: the same content under two users yields two unrelated ciphertexts. Security is paid for in storage space, and the trade-off is explicit and owned.

Manifests: the encrypted memory of files. Chunks are anonymous; the file manifest is the object that ties them together. It contains the file name, its size, its modification date, the ordered list of chunk addresses, and the envelope of the file key. The entire manifest is encrypted under the account key, with its dedicated domain context. Note what is encrypted: the file name is inside. Names, directory structure, extensions are metadata as sensitive as the content. Server-side, a manifest's only identity is an opaque random identifier. And the order of chunks is integrity data: it lives inside the authenticated blob.

The encrypted Merkle tree. Each directory is a tree object listing its children: confidential name, plus a reference to a file manifest or a subtree. The root references everything: knowing the root means being able to rebuild, with the keys, the complete state of the vault. This structure, comparable to git's internal model, has three precious properties. Modifications are localized: changing one file only rewrites its branch. Snapshots are free: keeping an old root means keeping a complete, consistent photograph of the vault. And synchronization becomes a diff: comparing two roots is enough to know what changed. One robustness detail: child names are validated at sealing and at opening. No empty names, no dot-dot, no path separators, no duplicates. A forged blob containing a path traversal must fail at opening, before any client materializes anything onto a real disk.

Several devices, one root. Your laptop and your desktop sync at the same time. Each wants to advance the root. Who wins? The root pointer, server-side, is versioned and only updates through compare-and-swap: replace the root only if it is still at version N. The first device succeeds. The second gets a rejection, downloads the new root, merges locally, it holds the keys, then retries with the up-to-date version. This is the essence of zero-knowledge design: the root pointer is the single serialization point of the system, and the server arbitrates it while understanding nothing of what it orders. All the intelligence lives in the clients.

Let's be honest about what the server does see regardless: approximate blob sizes, the times you synchronize, the graph of references between manifests and chunks. Hiding that metadata is very expensive; a good threat model documents it as accepted rather than pretending to cover it.

Key takeaways. Content-defined chunking makes differential sync possible, and the pipeline stays streaming. Addressing by the digest of the ciphertext gives verifiable integrity and idempotence without leaking anything. No cross-user deduplication: convergent encryption exposes confirmation attacks. Manifests and tree objects encrypt the sensitive metadata, and names are validated against forged blobs. The Merkle tree localizes modifications, provides free snapshots, and multi-device concurrency is settled by compare-and-swap on the root. What the server still sees is accepted and documented, not denied.
