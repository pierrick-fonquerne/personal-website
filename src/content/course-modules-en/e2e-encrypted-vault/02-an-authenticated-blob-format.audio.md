Chapter two. An authenticated blob format. AEAD, nonces, domain separation and a header covered by the tag: the four decisions that make an encrypted blob unreadable, unmodifiable, and unreplayable in another role.

Chapter one settled who holds which keys. This one decides what an encrypted byte looks like on the server's disk. It is a format-design exercise, and a storage format freezes fast: the first blob written in production must remain decryptable in ten years. Every decision made here is a near-permanent commitment.

AEAD: encrypting is not enough. Encryption alone guarantees confidentiality: without the key, the content is unreadable. It does not guarantee integrity: an attacker who cannot read can still modify, flip bits of the ciphertext and observe what decryption produces. The modern answer is AEAD: authenticated encryption with associated data. An AEAD primitive produces, alongside the ciphertext, an authentication tag: at decryption time, the slightest modification invalidates the tag and decryption fails, cleanly, revealing nothing. The A-D in AEAD matters just as much: associated data can be bound to the blob without being encrypted. It is not secret, but it is covered by the tag. Keep this intuition: associated data binds a ciphertext to its usage context.

Our primitive: XChaCha20-Poly1305, for two precise reasons. One: one-hundred-and-ninety-two-bit nonces. A nonce must never be reused with the same key. At that size, every nonce can be drawn at random: the collision probability is negligible. Short-nonce variants require synchronized counters, fragile in a distributed system. Two: constant-time execution everywhere, including compiled to WebAssembly in a browser, where software AES implementations are notoriously tricky. And our web client will run precisely this cryptography in WASM.

The structure of a blob. Every encrypted object in the system shares the same structure: one version byte in the clear, a twenty-four-byte nonce in the clear, then the ciphertext and its tag. The nonce is cleartext out of necessity: you must read it to decrypt, and it is not secret. The version byte is cleartext for a deeper reason: crypto-agility. The day a primitive must be replaced, new blobs will carry version two, and the client must read the version before knowing how to decrypt the rest. A format without a version byte is a format you can only evolve by breaking everything.

The cleartext header must be authenticated. Here is the chapter's subtlest trap. The version byte sits outside the ciphertext. The tag covers the ciphertext, but who covers the version byte? Nobody, unless you are careful. An attacker could modify it without invalidating the tag. Today, with a single version, the effect is nil. But in a future two-version system, flipping a blob's label would send the decryptor down the wrong parsing logic: a cross-version confusion, classic hunting ground for format attacks. The fix costs zero bytes: fold the header into the associated data. The version byte stays readable in the clear, but modifying it invalidates the tag. General rule: every field the decryptor reads and interprets must be covered by the tag, whether encrypted or not. Authenticate everything you parse. And this kind of fix must land before the first production blob: afterwards, it is a full format migration.

Domain separation: one blob, one role. Picture the complete system: key envelopes, file metadata, directory objects, data chunks, all encrypted, many under the same account key. What happens if the server serves one blob in place of another? If nothing distinguishes them, decryption succeeds, the key is right, and the client interprets valid bytes in the wrong role. That is a type-confusion attack, cryptographic edition. The defense is elegant: every blob family gets a unique context string, passed as associated data. Account-key envelope under the master key, envelope under the recovery key, file-key envelope, file manifest, tree object, data chunk: six distinct contexts. A blob sealed with the manifest context can only be opened with that same context. Every blob is cryptographically bound to its role. The server can shuffle blobs all it wants: the client detects it every time.

Note the refinement on the account-key envelopes: the master envelope and the recovery envelope carry different contexts. That is defense in depth: the distinction costs two string constants and turns a silent confusion into a clean failure.

One last detail: at decryption time, every failure cause, wrong key, modified data, wrong context, produces the same generic error. Distinguishing causes would hand an oracle to an attacker able to observe failures. On cryptographic failure, fail indistinguishably.

Key takeaways. An encrypted storage format is a long-term commitment: fixes happen before the first production blob. AEAD brings integrity, and associated data binds each blob to its context. Long random nonces eliminate counter coordination. The cleartext header must be authenticated: folded into the associated data, it stays readable but tamper-proof. Domain separation turns any blob shuffling into a detectable failure. And decryption errors are opaque, so as not to provide an oracle.
