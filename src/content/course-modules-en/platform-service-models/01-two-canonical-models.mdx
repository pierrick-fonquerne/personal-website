Imagine you are building a development platform: a source code management service, a deployment service, a feature flag service, a project management service. Very quickly, something becomes obvious: all these services talk about the same things. A "project". An "environment". An "organization". The user, however, sees only one: _their_ project, which has code, deployments, flags and a backlog.

The question that shapes the platform's entire architecture fits in one sentence: **who owns these cross-cutting concepts?** Does each service keep its own copy? Is there a central shared entity? The answer commits everything: the ability to ship services separately, the smoothness of the integrated experience, the cost of evolving the system.

By the end of this chapter, you will be able to recognize the two canonical models that dominate the market, explain their strengths and weaknesses, and understand why neither is enough when you want both autonomous building blocks and an integrated platform.

<Callout kind="info" title="Prerequisites and level">
**What you need to know**: the basics of service-oriented architectures (a service exposes an API and owns its data) and the notion of an entity in a data model.

**What you do not need to know**: Domain-Driven Design. Bounded contexts, shared kernel and published language are introduced in chapter 3.

</Callout>

## The problem of cross-cutting concepts

Let us state the problem precisely, because it is more subtle than it looks.

A feature flag service needs to group its flags: call that grouping a _project_. A deployment service needs to target _environments_: production, staging, development. A source code service groups repositories, again by _project_. These concepts look extremely similar. Same name, same intuition, same position in the hierarchy: the organization contains projects, the project contains resources.

The temptation is immediate: "it is the same concept, let us model it once". That is exactly the temptation we need to examine, because the two big architecture families on the market answer it in opposite ways.

## Model 1: the integrated monolith

The first model is the one used by all-in-one DevOps forges and integrated software suites. There, the "project" is **a single central entity**, stored once, on which every feature depends: the code repository hangs off the project, the CI pipeline hangs off the project, the environments hang off the project, the feature flags hang off the project.

The benefits are real and immediate:

- **Perfect integration.** A "project" page shows code, deployments, flags and backlog without inter-service calls, without synchronization, without any possible inconsistency. Navigation is smooth because everything is _already_ joined.
- **One model to learn.** For the user as for the platform developer, there is only one definition of "project", with a single lifecycle.
- **Trivial transactions.** Creating a project and its default environment in the same database transaction: no distributed protocol to invent.

The cost is just as real, but deferred:

- **Impossible to ship one building block separately.** The feature flag service cannot exist without the core that defines the project. You cannot offer it as a standalone product, nor replace it with another, nor open it to independent adoption.
- **Evolution coupling.** Any change to the central entity potentially impacts every feature. The "project" schema becomes the bottleneck of every team.
- **Limited organizational scale.** Ten teams working on the same core step on each other. That is Conway's law in its most brutal form.

<Callout kind="note" title="A coherent choice, not a mistake">
  The integrated monolith is not an anti-pattern. It is an optimization choice: it maximizes
  integration and initial velocity at the price of modularity. For a single product built by a
  single team, it is often the right choice. The problem arises when the product strategy requires
  selling or opening the building blocks separately, because that requirement is structurally
  incompatible with the single central entity.
</Callout>

## Model 2: autonomous services

The second model is the one used by the large public cloud providers. Here, each service owns **its own resources** and knows nothing about the others. The storage service has its buckets, the compute service has its instances, the database service has its clusters. There is **no global "project" entity** shared across services.

How does the user find their way? Through three _a posteriori_ federation mechanisms:

1. **Normalized identifiers.** Every resource has a unique name structured by a global convention (a URI or hierarchical naming scheme). Any tool can designate any resource of any service without ambiguity.
2. **Labels (tags).** Free key-value pairs attached to resources. The decentralized equivalent of the "project": you put `project=my-app` on your instances, databases and message queues, and a grouping tool finds them.
3. **An aggregation console.** A presentation layer above the services, which queries each one and rebuilds a unified view. Integration is not in the data model: it is recomputed at display time.

The benefits mirror the monolith's costs:

- **Each service lives its own life.** It is designed, deployed, versioned and sold separately. One team per service, independent release cycles.
- **Local evolution.** Changing a service's internal model impacts nobody, as long as identifiers stay stable.
- **Proven organizational scale.** This is the model that allowed catalogs of hundreds of services to grow for twenty years.

And the costs mirror the monolith's benefits:

- **The integrated experience is a permanent construction site.** Every cross-cutting view (billing per project, deleting a whole project, access rights per project) must be built explicitly on top of the services, and maintained.
- **Consistency is soft.** Nothing guarantees that a `project=my-app` label is set everywhere, or spelled the same. Orphaned resources and incomplete groupings are everyday life.
- **The "project" exists nowhere.** It is only a convention. No service can rely on it contractually.

## The fundamental incompatibility

Put the two models side by side and the dilemma appears:

|                           | Integrated monolith          | Autonomous services          |
| ------------------------- | ---------------------------- | ---------------------------- |
| "Project" entity          | Single, central, contractual | Nonexistent (tag convention) |
| Ship one block alone      | Impossible                   | Natural                      |
| Integrated experience     | Native                       | Rebuilt, costly              |
| Cross-cutting consistency | Guaranteed by the schema     | Soft, best effort            |
| Evolving one service      | Coupled to the core          | Free                         |
| Organizational scale      | One core team as bottleneck  | One team per service         |

If your strategy requires _both_: autonomous building blocks, adoptable and replaceable one by one, **and** an integrated platform experience where the project really exists, then neither canonical model is enough. You need a third one, borrowing from both without inheriting their disqualifying flaws. That is the federated model, the subject of the next chapter.

<Callout kind="tip" title="The reflex to remember">
  In front of any platform, ask the revealing question: "if I want to deploy this service alone,
  without the rest, can I?" The answer immediately tells you which family you are in, and therefore
  which structural costs you will pay.
</Callout>

## Key takeaways

- Cross-cutting concepts (project, environment, organization) are **the** structuring question of a multi-service platform: who owns them?
- The **integrated monolith** centralizes: perfect integration, but no building block can live alone and the core becomes the bottleneck of every evolution.
- **Autonomous services** decentralize: each service is free and shippable alone, but the integrated experience must be rebuilt and cross-cutting consistency stays soft.
- The two models optimize opposite goals; when the strategy demands both at once, a third model is needed: **federation**, in the next chapter.
