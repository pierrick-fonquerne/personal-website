Chapter five. Dual write and the transactional outbox. We hardened the consumer in the previous chapter, but it all rested on a promise from the producer: to publish the message at the right moment. Yet publishing touches two worlds at once, its database and the broker, and nothing makes them atomic together.

Let us start again. In chapter four, the consumer became unbreakable: it deduplicates with its key, it respects partition ordering, and the atomicity of its inbox makes its idempotence true. But this assumes that the producer actually publishes its message when the business state changes. And there, a surprise: publishing is not a simple gesture. The service must write the order to its database, and announce that fact to the broker. Two distinct systems, two separate writes. What happens if the database says yes and the broker never hears the message? No redelivery will save it, because it never existed.

This is the trap of the dual write: two systems to modify for a single business action, with no transaction spanning both your database and the broker. Look at the two ways of doing it. First way, write the database first, publish next: if the crash falls between the two, the order exists but the message is lost, and the payment will never be triggered. Second way, publish first, write the database next: if the crash falls between the two, the broker received a message for an order that, in the database, does not exist, a phantom message. Lost or phantom, the flaw is the same: between the two writes slips a moment where a crash can desynchronize them.

The idea of the outbox has a fine pragmatism: since we cannot make two systems atomic, we write only one. The service writes, in its own database, the business state and a row describing the message to send, all in the same transaction. This table of pending messages is the transactional outbox. Since the order and the outbox row share a single transaction, a crash can no longer separate them: either both are there, or neither. The lost message becomes impossible, because the message is no longer a fragile publication to another world, it is a plain row in the transaction that creates the order.

But a row in a table does not send itself. We need an outbox relay: a separate process, whose only task is to read the pending rows, publish them to the broker, then mark them as sent. And here is the subtle point: the relay too can publish a message then crash right before marking it sent. But this time it does not matter, because the row is still marked pending in the database, so on restart the relay finds it and republishes it. The price is a possible duplicate, and we recognize at-least-once delivery from chapter three. This is exactly where we reap what we sowed in chapter four: this duplicate is absorbed by the idempotent consumer. The producer-side outbox and the consumer-side inbox are the two jaws of the same pincer.

In the component, you can run the same order through both methods, the naive dual write and the outbox, and choose the crash point. With no crash, both work. But place the crash between the two writes: in dual write, the database keeps the order and the broker stays empty, inconsistent, message lost. In outbox, the two writes were in a single transaction, the crash did not separate them, the relay restarts, finds the pending row and publishes. Consistent, delivered after recovery.

One last point. A single relay becomes a bottleneck, we want several in parallel. But if two relays land on the same row, they both publish. The guard is the row claim: each relay claims its rows with a lock, in SQL the for update skip locked clause, which takes the free rows and skips those another has already locked. And a trap I really ran into while building Hexeract's outbox: the claim sets a lease, a duration during which the row is considered taken. I had sized this lease to the duration of a single publication, but a relay claims a batch and publishes it row by row, so the lease of the last rows expired before we reached them, and another relay republished them. The fix: size the lease to the number of rows in the batch multiplied by the duration of one publication. A lock only protects as long as it lasts.

In code, the pact is the same in both ecosystems: write the business state and the message in the same transaction, and let the message leave only after the commit. Hexeract offers an idempotent insertion into the outbox, keyed on the event id, and a relay that polls the pending rows under for update skip locked then marks them sent. Wolverine, on the .NET side, provides the same pact turnkey with its durable outbox: on a Marten transaction, the published message leaves only after the commit. Two languages, one idea: we never write the broker and the database in two separate gestures.

The chapter ends with two paper-and-pencil exercises, solved line by line: describe the two faces of the dual write, the lost message and the phantom message, and follow a relay that falls right after publishing, before marking the row sent.

In one sentence. We cannot make a database and a broker atomic, so we write only one world: the business state and the message leave together in a transaction of the database, the transactional outbox, then a relay publishes at-least-once what the transaction sealed, and the idempotent consumer of chapter four absorbs the duplicates.

Towards chapter six. The outbox and the relay guarantee that the message always ends up leaving. But the relay republishes as long as a message is not marked sent, and the consumer retries as long as a processing has not succeeded. What happens if a message can never be processed, because it triggers a bug every time? We would replay it indefinitely, and it could block the whole queue behind it. Chapter six, when a message is poison, learns to recognize these messages, to bound the attempts with a progressive backoff, and to set them aside cleanly in a dead-letter queue.
