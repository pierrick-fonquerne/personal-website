Chapter one. The three families of messages. The previous chapter set the command against the event. But asking for information is neither one nor the other, and it is this third family that we will name today.

Pick up the scenario from chapter zero, just before the payment. The order service must first check that the customer's card has not expired. Now, asking "is the card valid?" is not ordering anything, and it is not stating a fact that already happened either. It is a new intent: to ask. We call it a query message. A query puts a question to a specific recipient and always awaits data in return, without changing any system state.

The mailbox analogy still holds, but it needs refining. A command is dropping a note in a box and walking away. A query is stepping up to a counter: you ask your question, and you stay there while the clerk checks the register and answers you. You wait for the answer, but you asked for nothing to change.

So why separate the query from the command, since both address a single recipient? Because they do not do the same thing to the system. The command writes: it changes a state, a payment charged, a stock decreased. The query only reads: it returns information without touching anything. This distinction has a name, command-query separation, stated by Bertrand Meyer in nineteen eighty-eight. It says an operation must do one or the other, never both: either it changes state and returns nothing useful, or it returns data and changes nothing. The payoff is huge, because a query is safe to replay, running it ten times changes nothing, whereas a replayed command charges ten times.

We can now file any message with two questions, asked in order. First question: is the message addressed to a single known recipient, or broadcast to unknown subscribers? If it is broadcast and the sender awaits no return, it is an event, and the second question does not even arise. Second question, only for addressed messages: does this message write the state, or only read it? If it writes, it is a command. If it reads, it is a query. Keep in mind that command and query resemble each other in form but differ in effect, write versus read, while query and event resemble each other in the absence of an order but differ in reach, a single recipient versus a broadcast.

In the interactive component, you can sort six messages drawn from our e-commerce order into three bins yourself, command, query, or event, then check your sorting: every misplaced card reveals its true family and the reason, along the two axes we just laid out.

In code, frameworks route each family differently, and this is where the mediator appears, the piece we used in chapter zero without naming it. The mediator is the object that, in memory and inside a single process, receives a message and routes it to the right handler: one for a command or a query, zero to many for an event. When services live on different machines, that role is played by a bus or a broker, which carries the message over the network: that is the box chapter two will open. With Hexeract, in Rust, each family has its own verb: send to order, query to ask, publish to broadcast, and command-query separation is even written into the types. With Wolverine, in dot net, the query has no dedicated verb, it borrows the request-reply channel, the same method as the command that returns a result. Two legitimate philosophies, and what to take away is that intent comes before the framework's verb.

The chapter ends with two pen-and-paper exercises solved line by line: sorting six messages into the three families, then repairing an operation that violates command-query separation by splitting it into one command and one query.

In one sentence. Every message belongs to one of three families, told apart by two questions: broadcast to unknowns, it is an event; addressed to a single recipient, it is a command if it writes the state, a query if it only reads it.

Towards chapter two. We now know what we send, but we still treat the mailbox as a black box. Yet there are two great ways to build it: the broker, which delivers each message then forgets it, and the log, which keeps everything in order so each consumer rereads at its own pace. Chapter two opens that box and pits these two worlds against each other, RabbitMQ versus Kafka.
